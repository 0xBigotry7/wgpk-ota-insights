# 酒店 OPERA 经营日报接入核对单

## 已完成

独立经营报表归档 → 校验原附件 → 数字聚合解析 → OTA 工作台，自动检查频率为每 30 分钟。
不改前台入住/退房同步，不抓客人明细，不改房价、库存或评价系统。

## 需要 OPERA 账号持有人完成／协助的发送端核验

1. 进入 OPERA Cloud 的 Report Scheduler，找到 **History & Forecast**（原始文件名为 `history_forecast_…txt`）任务。
2. 数据范围选择**酒店整体、逐日期汇总**；不要仅某个房型，也不要把分房型与合计行混在同一导出里。
3. 输出使用现有同类 **制表符分隔 TXT/TSV 数据导出**，不是 PDF。需要字段：
   `REC_TYPE`, `CONSIDERED_DATE`, `CF_OCCUPANCY`, `CF_AVERAGE_ROOM_RATE`, `REVENUE`, `NO_ROOMS`, `INVENTORY_ROOMS`。
4. 历史/未来日期范围随酒店业务日滚动，覆盖昨天的实绩与今天开始的未来日期；不要固定在 7 月的旧参数。
   具体相对日期选项名称以酒店的 OPERA 版本为准。若只有未来数据、缺少实绩分界，先由我们核验日期元数据，不能猜成今日数据。
5. 收件地址保持 **opera-analytics@wyndhamgardenkamala.com**。
   不要替换现有 `opera-inhouse@…` 或 `opera-departures@…` 的收件地址/任务。
6. 先手动执行一次当前报表，保留 OPERA 的执行/投递结果；确认发件地址符合现有 `wyndham.com` 信任域。
7. 测试送达后，安排酒店当地时间夜审完成后的每天一次（由酒店确认实际时间和业务日）。
8. 核验报表币种、房量范围、收入是否含税及其计算范围；币种不凭酒店所在地猜测。

## 验收（不能只看任务显示“执行成功”）

- 专用归档 D1 出现新的收件时间和附件，R2 附件校验成功。
- OTA 工作台 `revenue.feed` 的最后归档时间与来源日期确实前进；新附件归档后，在下一个半小时检查入库。
- 来源“业务分界日”与报表实际业务日一致，界面不再显示 7/28 的旧经营数据。
- 对同一附件再次检查，新增快照数为零；入住/退房链路仍 fresh。
- 若 OPERA 显示已投递但归档没有收件，需要有 Email Routing 权限的 Cloudflare 管理员核对
  `opera-analytics@… → wgpk-opera-analytics-email-ingest` 规则及错误日志；本次现有 OAuth 对该规则读取返回 403，未擅改规则。
